## Causes ruled out

- **Temperature:** 68–75 °C in every case (limit 80 °C). Not thermal.
- **Clocks:** `glxgears` 1080p without vsync = 1621 FPS.
- **`amdgpu.dpm=0`:** tested with and without; the hang is identical.
- **VRAM/RAM:** 615 MB VRAM used at failure, 4.7 GB RAM free.
- **`amdgpu.dc=0` / forced EDID:** the failure is the same; `vkcube` never fails.
- **`RADV_DEBUG=llvm`:** avoids the hang but breaks pipeline creation.
- **DXVK GPL off:** the hang persists.
- **`devcoredump`:** empty (0 bytes) even after the failed reset.

## Conclusion

The bug is in **RADV from Mesa 26.0.8** with the gfx7 "Liverpool" GPU under DXVK
load. Mesa 25.3.5 and 26.0.4 from the same repo (with their Arch Archive LLVM)
work reliably. For 32-bit games there is no old RADV available (only
`lib32-llvm` 23.x), so wined3d/OpenGL is used.

## Heroic Launcher (Flatpak) — 2026-10-30

Heroic `com.heroicgameslauncher.hgl` v2.22.4. Inside its sandbox there was no
access to `/dev/dri` (the user override had `devices=!all`) or to
`~/mesa-versions`, and Mesa 25.3.5 lacked 3 libraries the runtime does not ship
(`libdisplay-info.so.3`, `libSPIRV-Tools.so`, `libedit.so.0`).

Fixed without root:

```bash
flatpak override --user --device=all \
  --filesystem=/path/to/repo \
  --filesystem=/home/USER/mesa-versions com.heroicgameslauncher.hgl
cp /usr/lib/{libdisplay-info.so.3,libSPIRV-Tools.so,libedit.so.0} \
   /path/to/repo/mesa-versions/deps/
```

Tests inside the sandbox (with `check-heroic.py`):

| Test | Result |
|---|---|
| `ldd libvulkan_radeon.so` with `deps/` | no missing libraries |
| `ls /dev/dri` inside the sandbox | `card0` and `renderD128` visible |
| Enumerate GPUs with Mesa 25.3.5 | 1 GPU: `AMD Jaguar (RADV LIVERPOOL)` |
| Enumerate GPUs with Mesa 26.0.4 | 1 GPU: `AMD Jaguar (RADV LIVERPOOL)` |
| `vkcube` inside the sandbox (wrapper) | renders the cube, 0 GPU failures |

`heroic-mesa.sh` is set as the game's *Wrapper command* and appends the paths to
the end of `LD_LIBRARY_PATH` (Heroic puts the Wine ones first).
